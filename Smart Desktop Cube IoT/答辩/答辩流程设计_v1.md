## 二、系统架构（1分30秒）

### 讲述脚本

> "接下来看系统怎么实现。"
>
> 【翻到PPT第5页：硬件架构图】
>
> "主控是ESP32-S3，双核240MHz，16MB Flash加8MB PSRAM。我们利用双核做了物理隔离——Core 0跑网络和通信，Core 1跑UI和传感器，两核之间通过共享数据池通信，互不阻塞。"
>
> "传感器方面，六种环境参数全覆盖：ENS160出CO2、TVOC、AQI、eCO2四项空气质量指标，AHT20出温湿度，BH1750出光照，LD2410B毫米波雷达做人体存在检测——这个是后面专注模式的核心。"
>
> 【翻到PPT第6页：软件分层图】
>
> "软件分三层：底层是FreeRTOS任务调度，中间是数据池加协议栈，上层是LVGL界面和Web服务。所有LVGL渲染严格限制在单一线程内，其他任务只写共享字段——这是我们踩了线程安全的坑之后确立的核心原则。"
>
> 【翻到PPT第7页：云端架构图】
>
> "云端走MQTT协议，自研握手鉴权——设备上报DID，后端下发Token，后续所有消息带Token校验。后端用FastAPI，接了大模型API做环境报告的智能生成。"

### PPT内容

**第5页（硬件架构图）**
- 【图片位】系统硬件连接图（ESP32-S3居中，各传感器用线连接，标注接口I2C/UART/SPI）
- 双核分工用两种颜色区分：Core 0（蓝色）= WiFi/MQTT/Web，Core 1（绿色）= LVGL/传感器/OTA
- 右下角小图：实物照片（外壳装好后的正面照）

**第6页（软件分层图）**
- 三层架构图：
  - 底层：FreeRTOS（Task_LVGL / Task_Network / Task_DataRead / Task_Control / OTA）
  - 中间层：DataPool共享数据池 + MQTT协议栈 + WebServer RESTful API
  - 上层：LVGL UI（bootScreen/mainScreen/fouseScreen/settingsScreen）+ Web控制页
- 用红色虚线框标注"LVGL线程安全边界"

**第7页（云端架构图）**
- 数据流图：ESP32 → MQTT Broker → FastAPI后端 → LLM API → 报告生成 → 网页展示
- 旁边标注：握手鉴权流程（DID→Token→带Token通信）
- 小图标：微信推送、网页数字孪生

### 演讲要点

## 评委提问预判 + 应答准备

### 高概率问题

**Q1: "你们和市面上的桌面温湿度计有什么本质区别？"**
> 答：它们是测量工具，显示数字就结束了。我们是决策终端——测量之后有判断、有行动、有推送。比如CO2超标，温湿度计只会显示一个数字，我们会判断"空气质量差"，推送微信通知，小眠表情变成告警状态，周报里会告诉你"这周有三天CO2超标，建议改善通风"。从测量到决策到行动，这是本质区别。

**Q2: "AI具体用了什么？是调API还是有自己的模型？"**
> 答：两端都有。端侧是TinyML的轻量PM2.5预测模型，跑在ESP32-S3上，不依赖网络。云端是大模型API做环境报告生成，但核心价值不在API本身，在于我们的数据聚合和prompt设计——我们把雷达存在数据、环境六参数、专注时长做跨源关联，这是通用大模型做不到的，因为它没有这些数据。

**Q3: "代码是自己写的还是AI生成的？"**
> 答：架构设计是我们自己做的——双核怎么分、协议怎么走、状态机怎么转、线程安全怎么保证，这些设计决策是人做的。实现层面我们大量使用了AI辅助编码，这在2026年是正常的工程实践。关键是每一个设计决策我都能解释为什么这么做——比如为什么LVGL必须单线程、为什么OTA要暂停其他任务、为什么I2C要做总线恢复。工具是AI的，脑子是我们的。

**Q4: "毫米波雷达和摄像头方案比有什么优势？"**
> 答：三个优势。第一，隐私——雷达不采集图像，放在卧室、宿舍没有隐私顾虑，摄像头不行。第二，穿透性——雷达可以穿透塑料外壳，不需要开孔，摄像头必须露出来。第三，功耗和成本——LD2410B几块钱，摄像头加AI推理芯片贵得多。对于"有没有人"这个判断，雷达是更优解。

**Q5: "这个产品能商用吗？壁垒在哪？"**
> 答：硬件本身没有壁垒，谁都能抄。壁垒在数据——跑三个月、半年之后，我们的决策模型比任何新入场的团队都准，因为我们有真实的环境-行为关联数据。另外用户习惯和角色IP的情感连接也是软壁垒。商用路径上，短期内可以走众筹/小批量，中期对接智能家居生态。

**Q6: "为什么选ESP32-S3而不是其他方案？"**
> 答：三个原因。第一，双核240MHz性能够跑LVGL加传感器加网络，不需要额外的应用处理器。第二，8MB PSRAM让LVGL的帧缓冲可以放PSRAM，内部RAM留给任务栈。第三，乐鑫生态成熟，WiFi/BLE/OTA都是现成的，开发效率高。这个赛道本身就是乐鑫命题，用ESP32-S3是最自然的选择。

**Q7: "专注模式的误触发怎么处理？比如只是路过桌子？"**
> 答：我们做了延迟确认机制——雷达检测到人体存在后，不是立刻进入专注，而是等待5秒持续存在才确认进入。同样，离开后也是5秒无人才退出。另外有30秒冷却期——手动退出后30秒内不会自动重新进入，防止"我只是站起来拿个东西"的误触。

### 中概率问题

**Q8: "MQTT为什么不用TLS？"**
> 答：当前是局域网场景，设备和后端在同一WiFi下，风险可控。协议层已经预留了Token鉴权，后续上公网时可以加TLS。这是一个工程权衡——局域网内TLS的握手开销对ESP32来说不小，在演示场景下我们优先保证通信稳定性。

**Q9: "传感器数据准不准？有没有校准？"**
> 答：ENS160有72小时预热期，我们上电后持续运行让传感器稳定。AHT20出厂已校准。BH1750是数字输出，精度高。实际使用中我们更关注趋势和相对变化（比如"CO2从600升到1200"），而不是绝对精度。周报里的洞察也是基于趋势分析。

**Q10: "团队怎么分工的？"**
> 答：我负责硬件和固件——系统架构、双核任务设计、传感器驱动、LVGL界面、OTA。成员2负责后端——FastAPI服务、MQTT通信、AI报告生成、数字孪生网页。成员3负责测试、文档、PPT和演示视频。三个人从四月开始，每周至少碰一次进度。
